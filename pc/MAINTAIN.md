# 维护指南（给下一个改这份代码的人，人或 AI）

这份文档记录**为什么代码长这样**，而不是它做了什么（做了什么代码里写着）。
改之前先读完，能省掉重复踩坑。所有"实测"都是在本机真跑出来的数字，不是估计。

---

## 1. 程序长什么样

```
app.py ── 启动本地服务(127.0.0.1:8765) ── 用 Edge 的「应用窗口」打开 http://127.0.0.1:8765/
  │                                            │
  └── server.py（纯标准库 HTTPServer，多线程）  └── web/（原生 HTML/CSS/JS，无框架）
          ├── bili.py          搜索 / 取纯音频流（B 站公开接口）
          ├── qqmusic.py       解析 QQ 音乐歌单（只取元数据）
          ├── downloader.py    下载 + AAC→MP3 转码
          ├── store.py         library.json（原子写入 + .bak 备份）
          ├── share.py         歌单分享文本编解码
          ├── linkparse.py     链接识别（歌单 / 视频 / 分享文本）
          ├── hotkeys.py       全局热键
          └── paths.py         资源目录 / 数据目录分离
```

**必须理解的一条**：`paths.py` 把路径分成两种。

- `res_dir()` 只读资源（`web/`、图标、`ffmpeg.xz`）。打包后指向 `sys._MEIPASS`，每次启动重新解压，**不能往这里写**。
- `data_dir()` 可写数据（歌单、设置、登录 cookie、转码缓存的 ffmpeg）。永远在 **exe 旁边**的 `data/`，源码直跑时就是 `pc/data/`。

写错这两个的后果：打包后每次启动设置全丢，或者数据被写进临时目录——用户会以为"设置没保存"。

## 2. 网络层：这是全部麻烦的来源

B 站对脚本请求有风控。这段是踩完之后定下来的，**别轻易"简化"**。

### 2.1 搜索接口的选择

| 接口 | 需要签名 | 用途 |
|---|---|---|
| `x/web-interface/wbi/search/type` | 要（WBI：wts+w_rid） | 主通道，结果字段规整 |
| `x/web-interface/search/type` | 不要 | 降级通道，字段同构但 `play`/`video_review`/`favorites` **是字符串** |

老接口的字符串字段必须转 int 再排序，否则 `key=lambda r: -r["play"]` 会直接抛 TypeError。
这个坑已经踩过一次，处理在 `bili._parse_results()`。

### 2.2 WBI 签名

算法是 B 站前端公开的：取 `nav` 接口返回的 `wbi_img.img_url` 和 `sub_url`，各截取文件名（去掉扩展名），
拼成一个 64 字符的串，按 `MIXIN_KEY_ENC_TAB` 重排，取前 32 位当密钥；
请求参数按 key 排序、过滤 `!'()*`、URL 编码，末尾拼上密钥做 MD5，作为 `w_rid`，同时带上 `wts=当前秒`。

密钥缓存 1 小时。`nav` 接口拿不到 wbi_img 时说明网络或风控异常，抛 `BiliError`。

### 2.3 已知的风控表现（按严重程度）

1. **返回空但 code=0**，`data` 里只有一个 `v_voucher` —— 最常见的软风控。
   应对：`_search_wbi()` 会模拟打开一次搜索页、退避 0.8~2.0 秒再试，最多 4 次。
2. **`code=-111 message=csrf 校验失败`** —— 账号/IP 级的硬风控，会连续拒一段时间。
   曾经的表现是界面连弹四条"搜索失败：搜索失败：csrf 校验失败"。
   应对（2026-10-29 加）：主接口失败 → 老接口 → 换匿名身份再试两个接口，全挂才报错。
3. **`code=-352 / -412`** —— 请求被拦截。应对：退避 1.2/2.4 秒重试，**不换设备指纹**。

**为什么不在重试时换 buvid3/buvid4**：风控会记住设备指纹，一个进程每次启动都换新指纹，
比"一直是同一个"更像临时爬虫；而且登录态是绑着登录时那枚 buvid 的。现在只有真的缺 buvid3 才向
`x/frontend/finger/spi` 要新的。

### 2.4 Referer 必须是带关键词的搜索页

实测：`Referer: https://www.bilibili.com/` 或不带关键词的搜索页地址，绝大多数请求只回一个
`v_voucher`（结果为空）；换成 `https://search.bilibili.com/all?keyword=<URL编码后的关键词>` 后基本 100% 成功。
这条改回去会让搜索"时好时坏"。

### 2.5 `order` 参数不要传给服务端

带 `order`（点击/最新/弹幕/收藏）去请求，服务端更容易直接甩 v_voucher 空结果。
现在是拿到结果后在本地排序，效果等价，且不触发风控。排序在 `bili._sort_results()`。

### 2.6 限流与缓存

- 两次搜索请求之间至少间隔 0.35 秒（`_throttle()`，实例级锁）。
- 同一 `(关键词, 页码, page_size)` 的结果缓存 **10 分钟**（`_search_cache`）。
  翻页、「加载更多」、反复搜同一个词都不再打接口——重复搜索是触发风控最直接的原因。
- 登录态的 cookie 只存 `SESSDATA / bili_jct / DedeUserID` 等，
  **`_PRIVATE_COOKIE_KEYS` 里的字段不会写进匿名缓存文件**，避免退出登录后被写回。

### 2.7 懒匹配（只搜一次）

QQ 音乐歌单是"秒导"：导入时只存元数据，`bvid` 是 `qq_<mid>` 占位符，首次播放才去搜一个真实音源。
匹配成功后**全局就地替换**（所有歌单 + 播放历史），每首歌只搜一次。
这不是为了快，主要是为了少触发风控。改这里之前想清楚：批量重搜 = 主动招风控。

## 3. 下载与转码

音源是 B 站 DASH 里的**纯音频流**（不碰视频），实际是 192K AAC / MP4 容器。
旧版本直接存成 `.m4a`，但文件头是 `ftyp isom ... mp41` 且带 `moof` 分段，很多设备/剪辑软件打不开。

现在：下完立刻转 **320K CBR MP3**，转成功删掉 `.m4a`；转失败保留 `.m4a` 并如实提示。
不选 VBR / 不选 192K 的原因：源是 192K AAC，AAC→MP3 是二次有损，给到 320K 才不会在这一档再削高频；
CBR 对车机、老 MP3 芯片、剪辑软件最省事。代价是 4:30 的歌从 6.2 MB 变 10.3 MB。

**不要用系统里随便找到的 ffmpeg**：实测某些第三方构建缺 `libmp3lame`，或者依赖同目录私有 dll，
一搬走就报 `libpag.dll: cannot open shared object`。所以 `downloader.ffmpeg_path()` 会真转一小段做探测，
通过才用。源码直跑且没有 `ffmpeg.xz` 时，才会退回系统 PATH 里的 ffmpeg。

## 4. Windows 平台上的几个硬约束

| 现象 | 原因 | 现在的做法 |
|---|---|---|
| WebView2 白屏 / 崩溃 | 本机 msedgewebview2 启动即崩（`Error launching CrashSender.exe`） | 主用 `msedge --app=` 应用窗口，WebView 只作备选 |
| 任务栏图标变成 Edge 的 | `--app` 窗口默认挂在 MSEdge 这个 AUMID 上 | 传 `--app-user-model-id=CoconutMusic.App.1` 并在 HKCU 注册 DisplayName / IconUri |
| 双击两次开了两个 | 单实例 | 启动时抢命名互斥量 `Local\CoconutMusic.SingleInstance`，已在运行就把已有窗口切到前台然后自己退出 |
| 设置"没保存" | 数据写进了 `_MEIPASS` | 见第 1 节，可写数据一律走 `paths.data_dir()` |
| 窗口关不干净 / 点歌单提示"歌单不存在" | 拿 Edge 进程当"窗口还开着"的信号：Edge 对同一个 `--user-data-dir` 是单实例，已有 Edge 在跑时新起的 msedge 把窗口交给老进程后自己立刻退出，主程序便以为窗口关了先退，留下没有后端的空壳页面 | 退出条件改成"连续 3 秒看不见标题含「椰子音乐」的窗口"；不再 `proc.wait()` |

### 4.1 启动速度：别在启动路径上做"探测"

冷启动（双击到窗口出现）实测 **0.87~0.89 秒**，首次带杀软扫描约 1.4 秒。曾经是 3.1 秒，慢在两处探测，
都已经拆掉，别加回去：

| 曾经的做法 | 代价 | 现在 |
|---|---|---|
| 用 HTTP 请求 `127.0.0.1:8765/api/state` 判断有没有重复启动 | 没有实例在跑时，Windows 连本地**未监听**端口不会立刻拒绝，要把超时走满——白等 1.5 秒 | 命名互斥量，微秒级 |
| 服务起来后再轮询"能不能访问" | urllib 在本机首次请求本地服务另有约 0.4 秒客户端开销（裸 socket 首包只要 17 ms），而 `ThreadingHTTPServer` 构造时就 bind+listen，连接会排进 backlog | 直接删掉 |

单文件解包占约 0.5 秒，Python 初始化与导入约 0.15 秒，Edge 应用窗口冷启动约 0.3 秒——这些是当前形态的下限。
把 22.9 MB 的 `ffmpeg.xz` 从包里拿掉实测没有区别（0.79/0.84/0.96 秒），解包是顺序拷贝、不费 CPU，所以没拿。

复测方法：从 `Start-Process` 计时到 Edge 窗口 `MainWindowHandle != 0`，每次先杀干净旧进程与旧 Edge 再跑；
同一份代码跑三次取中位，别只跑一次。

## 5. 改完之后怎么验证

1. **搜索链路**：`python test_search.py`（在本目录）。
   覆盖：正常搜索、缓存命中（第二次不该有请求）、强制主接口返回 -111 时自动降级、
   全通道失败时的文案、老接口字符串字段转 int。
2. **起服务**：`python app.py`，会占 8765。要单独测后端可 `python server.py`。
3. **打包**：`pyinstaller 椰子音乐.spec --noconfirm`，产物在 `dist/`。
   打包后**必须**检查两件事：`data/` 是否还在 exe 旁边、`web/` 有没有被漏打（漏了就是白屏）。
4. **隐私**：发布前扫一遍 exe 原始字节，确认没有用户名、cookie 值、源码绝对路径、歌单里的歌名。
   历史上确实靠这一步发现过泄漏。
5. **启动与单实例**（`app.py` 动过就必须做）：
   - 冷启动记时（方法见 4.1），超过 1.5 秒就要找原因；
   - 开着的时候再双击：应把已有窗口切到前台、自己 1 秒上下退掉；
   - 关掉窗口 1 秒内再双击：应该能正常开起来（走"上一个实例正在退出，本次接手启动"）；
   - 点开一个歌单：不该出现"歌单不存在"（那说明后端已经退了、窗口还在）。

## 6. 发布流程

1. 改代码 → 跑第 5 节的验证。
2. 打包 → 把 `dist/椰子音乐.exe` 传到 **Release**（不要塞进 git，39 MB 的历史负担消不掉）。
3. 仓库里只放源码 + `ffmpeg.xz` 的说明；**用户从 Release 下载成品，不从源码自己打包**。
4. Release 说明里写清这一版修了什么、还挂着什么。

## 7. 已知未解决

- **风控没有根治办法**。三级降级只是把"直接失败"变成"大概率还能搜到"，同一 IP 高频请求仍会被拦。
  真要根治得换请求出口或上官方开放平台接口，都不在本项目范围内。
- 搜索结果缓存 10 分钟，意味着新发布的视频最多晚 10 分钟才搜得到。
- 手机端（`mobile/`）是与 PC 端独立的单文件实现，两边的匹配算法是各写各的，改动不会自动同步。
